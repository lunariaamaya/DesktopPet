## 2. 仓库与分支

- 默认远端名 origin，主分支 main。先确认 GitHub 仓库 URL 和访问权限，不把 token 写入 URL。
- 新项目可先使用单主分支；较大功能用 feat/*、修复用 fix/*，合并前检查差异。是否启用 PR/分支保护随仓库设置确定，不强制七天 MVP 引入额外流程。
- 正式发布打 vX.Y.Z 标签并推送标签；发布说明注明对应提交和已验证平台。文档版本独立于程序发布版本。
- 提交信息建议 docs:/feat:/fix:/chore: 前缀，说明结果与目的；不伪造测试通过。
- 远端已有提交时先 fetch，检查分支与历史再整合；不盲目覆盖、强推或删除分支。

## 3. 同步流程

```text
检查 git status 和具体 diff
→ 确认只包含本批预期修改且无敏感数据
→ 完成必要验证（文档链接/差异，代码按变更运行检查）
→ git add 明确的文件
→ git commit
→ 推送到对应 origin 分支
→ 确认成功并记录提交号
```

仓库缺失、网络故障或认证失败：保存本地工作/提交，明确待同步原因；下次恢复后先补同步。不要重复索要已经提供的仓库信息，不在聊天中索要 token 明文。凭证通过系统凭证管理或用户已有登录配置提供。

## 4. 不入库与资产策略

.gitignore 已预留密钥、环境文件、数据库、聊天/记忆运行数据、导出、诊断、模型权重、构建目录和安装包规则。样例配置只写变量名或假值；不得包含真实 API Key、Cookie、私人文件路径列表。

忽略规则不是扫描器：每次提交仍检查实际清单。素材来源和许可随 manifest 入库；角色参考图若有隐私或权利限制，不因“版本管理”而默认公开。大体积动画/源文件评估 Git LFS；模型权重不入代码库。发布安装包走 Release 或选定分发存储，不塞入源码历史。
